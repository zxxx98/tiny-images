# 渠道并发设置设计

## 目标

为每个渠道增加可配置的并发上限，默认值为 2。所有经统一 `Executor` 发往同一渠道的生成和编辑请求共享该上限，超过上限的请求按进入顺序等待。

## 数据与接口

- SQLite `channels` 表新增 `concurrency INTEGER NOT NULL DEFAULT 2`，迁移时现有渠道自动得到 2。
- `ChannelConfig`、`ChannelRow`、`ChannelInput` 和 Web `Channel` 类型新增 `concurrency: number`。
- 仓储创建渠道时缺省为 2，更新时持久化该值；YAML 种子配置支持可选 `concurrency`。
- 管理 API 接受正整数 `concurrency`，非正数、小数或非数字返回 400。
- 管理端新建渠道草稿默认并发为 2，编辑表单提供最小值为 1 的整数输入，并在渠道列表显示当前并发。

## 执行模型

`Executor` 持有按渠道 ID 索引的自适应 FIFO 信号量。路由解析后、额度检查和上游调用前，请求获取该渠道的槽位；整个 Key 轮换和 provider 调用过程占用一个槽位，并在成功或异常时通过 `finally` 释放。

每次调用都会把信号量上限同步为渠道最新配置。调大时立即唤醒更多排队请求；调小时不取消正在执行的请求，但在活动数降至新上限以下前不再放行新请求。不同渠道使用不同信号量，因此互不阻塞。

## 错误与生命周期

并发值只允许大于等于 1 的整数，避免永久无法调度。上游成功、可重试错误、不可重试错误和同步异常都必须释放槽位。队列只存在于进程内，服务重启后自然清空；这与现有内存熔断和 Key 冷却协调方式一致。

## 测试

- 仓储测试覆盖默认值、显式创建值和更新持久化。
- 管理 API 测试覆盖默认返回、合法更新和非法值拒绝。
- Executor 测试用受控 Promise 证明同一渠道最多同时运行设定数量、排队请求在释放后继续。
- Web 测试覆盖新建草稿默认值；完整测试和构建作为合并前验证。
