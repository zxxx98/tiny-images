# 历史记录保留策略设计

## 目标

- 生成历史 `generations` 只保留最近 7 天。
- 历史图片继续使用现有 24 小时 TTL，不延长图片文件寿命。
- 图片失效后、历史记录到期前，历史页面仍展示 prompt、模型与生成参数，并允许用户“重新生成”。
- 管理员页面使用的 `request_logs` 只保留最新 50 条。

## 保留边界

生成历史按 `created_at` 判断。清理时删除严格早于 `当前时间 - 7 天` 的记录；恰好位于截止时间的记录仍保留到下一次清理。

图片文件与历史记录独立清理：图片仍在服务启动时及每小时按 24 小时 TTL 清理。删除图片不会删除或修改对应的 `generations` 行，因此第 2 天到第 7 天之间，历史详情仍可读取 prompt、模型和参数并重新生成，只是图片显示为“已过期”。

## 实现方案

在 `Repo` 中新增按截止时间物理删除生成历史的方法，并返回删除数量。服务启动时执行一次历史清理，随后每小时执行一次，与现有图片清扫采用相同调度频率但保持独立逻辑。

为 `generations.created_at` 增加数据库索引，避免历史数据增长后全表扫描。迁移只增加索引，不重写现有记录；首次启动新版本时，启动清理会移除已经超过 7 天的旧记录。

`request_logs` 沿用现有“每次插入后仅保留最新若干条”的物理裁剪机制，将上限从 1000 改为 50。因此升级后第一次新增请求日志时会把已有日志裁剪到最新 50 条。

## 错误与运行行为

清理操作使用本地 SQLite 和文件系统的既有错误处理方式。历史清理失败不应静默伪装成成功；启动阶段数据库错误继续按当前启动失败行为暴露。定时清理成功删除记录时写入数量日志。

本次不新增管理员配置项，不改变历史 API 响应结构，也不改变“重新生成”前端数据流。

## 测试与验收

- 仓储测试验证：早于 7 天截止时间的记录被删除，截止时间及之后的记录保留，并返回正确删除数量。
- 仓储测试验证：连续写入超过 50 条请求日志后，只留下最新 50 条。
- 既有历史 API 测试继续验证图片不存在时，历史元数据仍可查询；前端既有“重新生成”逻辑不做行为修改。
- 运行服务端完整测试、前端完整测试及整体构建。

## 非目标

- 不把历史图片 TTL 从 24 小时延长到 7 天。
- 不在删除历史记录时提前或额外删除图片文件；图片仍由独立 TTL 清扫负责。
- 不提供用户手动删除历史、管理员历史配置或恢复已过期记录的能力。
