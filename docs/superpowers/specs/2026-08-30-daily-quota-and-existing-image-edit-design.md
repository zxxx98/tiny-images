# 设计：每日额度刷新与已有图片编辑

## 目标

修复两个现有行为：

1. 普通用户的图片额度在北京时间每天 00:00 恢复为管理员配置的每日额度。
2. 从生成结果或历史记录带入已有图片后，点击“编辑”直接提交该图片，不再要求用户重新选择本地文件。

## 根因

`users` 表目前只保存 `quota_total` 和累计的 `quota_used`，没有额度所属日期，因此系统无法判断何时跨日。已有图片编辑链路已经把远端图片下载并转换为 `File` 存入 React 状态，但原生文件输入框仍固定带有 `required`；浏览器表单校验只检查 `input.files`，不会识别 React 状态中的文件。

## 每日额度设计

在 `users` 表新增可空的 `quota_day TEXT`，保存 `quota_used` 所属的北京时间日期，格式为 `YYYY-MM-DD`。日期由服务端使用 UTC 时间加八小时后计算，不依赖服务器操作系统时区。

Repo 层集中提供额度日期刷新逻辑：

- 读取单个用户、按邮箱读取用户、列出用户以及扣减额度前，检查 `quota_day`。
- 当 `quota_day` 为空或不等于当天日期时，用条件更新将 `quota_used` 清零并把 `quota_day` 更新为当天。
- 同一天内不修改已用额度。
- `chargeQuota` 先执行跨日刷新，再沿用现有条件更新，确保并发扣减仍不会超过 `quota_total`。
- 管理员和不限额用户保持原有行为；日期字段存在与否不改变“不限额”语义。

升级已有数据库时，旧用户的 `quota_day` 初始为空，因此部署后的首次额度读取或请求会进入新的一天并恢复额度。这正是从累计额度切换为每日额度时的预期行为。

## 已有图片编辑设计

保留当前“下载图片 → 转换为 `File` → 写入 `editFiles` → 切换编辑模式”的数据流。文件输入框的 `required` 改为仅在 `editFiles.length === 0` 时启用：

- 从结果区或历史记录进入时，`editFiles` 已有文件，浏览器不会再触发文件选择校验。
- 用户直接切到图片编辑且没有任何原图时，原生校验和提交按钮禁用逻辑继续阻止空提交。
- 用户手动选择文件的行为保持不变。

不绕过服务端校验；`/v1/images/edits` 仍要求至少一张图片。

## 错误与边界处理

- 北京时间日期计算必须覆盖 UTC 日期与北京时间日期不同的边界。
- 多次读取当天额度不能重复清零。
- 跨日后首次扣减必须基于清零后的额度执行。
- 已有图片下载失败时继续显示当前明确错误，不进入可提交状态。
- 数据库迁移只新增字段，不删除或重写用户、额度和历史数据。

## 测试与验证

- Repo 回归测试：当天累计保持不变；北京时间跨日时清零；跨日后可以重新扣减；条件扣减仍不超额。
- API/执行器回归测试：前一天耗尽额度的用户在北京时间次日可再次生成并正确扣减。
- Web 回归测试：已有 `editFiles` 时文件输入框不带 `required`，没有图片时仍带 `required`。
- 运行服务端全量测试、Web 测试和根目录完整构建。
- 最终检查迁移、接口返回、管理端额度展示和编辑表单均使用刷新后的状态。

## 非目标

- 不引入定时任务、额度流水或滚动 24 小时窗口。
- 不新增管理员手动清零按钮或可配置时区。
- 不改变管理员配置额度、按成功图片张数扣减及 HTTP 402 错误语义。
