# 历史图片真实分辨率设计

日期：2026-09-01

## 背景与目标

历史页目前只能从请求参数 `params.size` 推断普通生成图片的尺寸。请求没有指定尺寸时，该字段为 `auto`，但 `auto` 不是生成结果的实际分辨率。图片已经返回并能被服务端保存时，可以使用现有的 `sharp` 解码图片元数据得到真实宽高。

本次目标是：

1. 普通生成、图片编辑、流式响应和后台 job 的历史图片保存真实 `width`/`height`。
2. 超分历史图片也保存实际输出宽高，并让后台 job 接口与历史接口保持一致。
3. 历史墙和详情优先显示图片真实分辨率；旧历史记录没有元数据时，用浏览器加载后的 `naturalWidth`/`naturalHeight` 回退。
4. 保留旧历史 JSON 的兼容性，不增加数据库迁移。

## 方案与数据流

### 服务端

`localizeImage` 负责把 base64 或远程 URL 变成本地历史文件。它先取得图片 buffer，用 `sharp(...).metadata()` 解码并读取宽高，确认宽高是正整数后再保存文件，返回 `{ file, width, height }`。下载失败或无法解码时仍返回 `null`，沿用当前各调用方的错误处理策略。

将这个返回值贯穿到以下历史图片入口：

- 后台普通生成和编辑 job 的内存 job 与 `generations.images` JSON。
- 同步生成/编辑通过响应提取历史图片的路径。
- 流式生成/编辑记录历史的路径。
- Cloudflare 超分任务使用已经校验过的输出元数据保存 `width`/`height`。

`GET /v1/history` 和 job 轮询接口只在图片有尺寸时输出可选字段，因此没有尺寸的旧记录仍能正常返回；JSON 中不存在的可选字段不会被伪造为请求参数尺寸。

### 前端

`HistoryImage` 增加可选 `width`/`height`。历史尺寸的优先级固定为：

1. 服务端持久化的图片宽高。
2. 当前图片加载事件提供的 `naturalWidth`/`naturalHeight`。
3. 旧超分记录的 `params.targetWidth`/`targetHeight`。
4. 旧普通记录的 `params.size`。
5. 无法读取时显示 `未知`。

浏览器回退尺寸按“记录 id + 图片下标”保存，避免多图记录相互覆盖。墙砖封面和详情元信息都使用同一套格式化规则；图片过期时保留现有占位行为。

## 错误处理与兼容性

- 元数据解析失败视为本地化失败，不保存不可确认尺寸的历史图片；后台普通生成仍按当前逻辑跳过该图片，编辑和超分仍按当前逻辑将任务标记为失败。
- 历史数据库仍使用现有 `images` JSON，不增加列或迁移。旧对象只有 `file` 时，API 原样返回文件 URL，前端通过图片加载回填尺寸。
- 服务端不会修改 OpenAI 兼容的生成响应格式；真实尺寸是历史/job 图片元数据，避免向上游兼容响应添加非标准字段。

## 测试策略

- `b64cache` 单元测试验证 base64 与 URL 本地化返回真实宽高，并验证无效图片仍返回 `null`。
- 历史 API/job 集成测试验证尺寸从普通后台生成、同步记录和超分输出进入 job/history JSON。
- 前端回归测试验证服务端尺寸优先、旧 `auto` 记录初始显示 `未知`，图片 `load` 后显示 `naturalWidth × naturalHeight`，以及历史详情仍保持原有图片点击行为。
- 完成后运行 `npm test`、`npm run build` 和 `git diff --check`。
